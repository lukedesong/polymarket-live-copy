# Polymarket 钱包研究与纸面跟单全程复盘

## 目的

这份复盘不是解释某次失误，而是把整段对话中反复出现的决策错误转成可执行、可验收、会被项目自动加载的规则。强制规则已同步写入项目根目录 `AGENTS.md`。

## 证据与数字口径

- 对话中的领域占比、成交笔数、一分钟观察窗和纸面预算均为**用户指定值或用户举例**，不是已验证门槛。
- API 页大小、offset、具体市场当时的 `min_order_size` 属于**外部约束值**；必须按端点、市场和时间重新核验。
- 本文记录的服务状态、心跳、错误、Git 文件和调度器状态属于**实证值**，来自本轮本机 `date`、`launchctl`、`status.json`、plist 和源码只读检查。
- 无法从对话或本地持久证据恢复的旧故障根因，只记为“现象已确认、精确根因未知”，不事后编造解释。

## 总结：反复出现的根病

最核心的问题不是某个阈值设置错误，而是以下决策模式反复出现：

- 用容易计算的代理指标替代用户真正的经济目标；
- 把用户举例硬化成规则，或被纠正后机械摆向相反极端；
- 该自主判断时把决定重新甩给用户；
- 没先锁定统计对象和单位，就开始给精确数字；
- 把代码、单测、网页或进程启动当成生产运行完成；
- 用户纠正一个例子时只修那个点，没有修整类、所有实例和验收合同；
- 交付缺少地址、网页、状态、账务或即时证据，迫使用户反复追问。

## 全程失败清单与永久修复

### 需求与自主判断

#### 把用户的例子当成硬阈值

- **对话表现**：领域占比、成交笔数和一分钟观察直觉被机械写成资格或风险规则，用户不得不反复说明这些只是例子。
- **根因**：为了快速得到确定结论，把连续证据切成没有样本外依据的门槛。
- **永久规则**：用户举例先转为连续特征并标注来源；只有外部约束或冻结样本外证据才能成为承重门槛。
- **验收**：改变示例数字不得自动改变候选资格；任何承重数字都能追溯到公式、实证、外部约束或用户指定。

#### 纠正后从一个极端摆到另一个极端

- **对话表现**：先因中途卖出、篮子、做市或速度形态过度排除，随后又趋向“所有相关钱包都深挖，只有前瞻纸面能否决”。
- **根因**：顺着用户最新一句反向执行，没有建立分层证据和研究成本优先级。
- **永久规则**：分开行为描述、源经济性、复制先验、低成本验证和正式前瞻纸面。历史风险可降低优先级但不能靠标签误杀；无源经济性或研究价值的钱包也不必进入昂贵阶段。
- **验收**：每个候选同时给出策略类型、复制风险、下一证据成本和研究优先级。

#### 没有红队用户假设

- **对话表现**：“很多成交就是可靠回测”“整数亏损可能是人工冲动、小数盈利可能是 Agent”等假设没有第一时间检查替代解释。
- **根因**：把合作误解成支持用户猜想。
- **永久规则**：任何用户机制假设必须拆成成立部分、未证明部分、替代解释和可证伪测试；无法排除替代解释时只能标“待验证假设”。
- **验收**：分类规则不能使用最终输赢标签；盲化盈亏后仍应得到相同策略袖套或行为分类。

#### 已授权事项仍反复询问

- **对话表现**：用户已经确认纸面、要求直接上线或授权自行判断后，我仍让用户再次确认设计和边界。
- **根因**：把内部流程变成用户手续，并逃避判断责任。
- **永久规则**：只读分析、纸面研究和可逆修改在意图清楚时直接完成；只有新增权限、真实资金授权或无法从数据恢复且会实质改变结果的缺失项才问。
- **验收**：每次提问必须说明为什么数据无法获得，以及不同答案会如何改变结果；否则不应提问。

### 数据、字段与统计单位

#### 把公开接口记录说得接近“所有交易”

- **对话表现**：用户连续追问能否看全部交易、完整输赢以及能看多久。
- **根因**：没有先说明代理钱包、端点、分页、开放仓、结算、未成交挂单、撤单、链外对冲和其它账户边界。
- **永久规则**：任何账户先交付 coverage manifest；无法证明完整时禁止使用“所有”“完整”。
- **验收**：报告列端点、起止时间、行数、唯一交易、独立事件、分页、截断和未知项。

#### 混淆 BUY/SELL 与 maker/taker

- **对话表现**：用户需要追问“主动成交方向”和“是不是都是 taker”。
- **根因**：没有把用户交易方向、成交发起角色和订单簿角色分层解释。
- **永久规则**：BUY/SELL 只描述钱包对 outcome 的方向；缺独立字段或链上证据时 maker/taker 写未知。
- **验收**：不得由 `side` 字段直接推断做市商。

#### 把 fill 行当成订单、决策或仓位单位

- **对话表现**：极小成交碎片被用于推导固定比例，产生异常大的资金结论，用户看到源账户小数成交后才发现问题。
- **根因**：Data API 没有完整源订单边界，却把最小 fill 当成最小源动作。
- **永久规则**：fill、链上交易、逻辑动作、订单和决策分层；动作边界不可恢复时 `BLOCK_ACTION_RECONSTRUCTION`。
- **验收**：同一订单被拆成更多 fill 不得改变策略频率、有效样本或资金比例结论。

#### “每天几笔”没有固定单位和分母

- **对话表现**：日均交易可能实际统计了 fill 行，而用户关心的是可复制动作负担。
- **根因**：使用最方便的 API 行数。
- **永久规则**：同时给 fill、唯一交易、逻辑动作和事件；说明按全部日历日还是活跃日及所用时区。
- **验收**：候选排序不能因拆单方式改变而无解释翻转。

### 策略与统计推断

#### 把钱包历史称为“真实回测”

- **对话表现**：大量真实成交一度被当作足够的回测结果。
- **根因**：混淆观察性实盘轨迹、源策略回测和我方跟单回测。
- **永久规则**：钱包历史只能证明源账户在可见轨迹上的结果；必须披露幸存者偏差、选择偏差、未知对冲、策略换挡和我方执行差异。
- **验收**：没有我方样本外延迟成交证据，不得写“可实盘复制”。

#### 把成交行数当成独立样本量

- **对话表现**：围绕数千或更多成交讨论可靠性时，没有先扣除拆分 fill、同一事件多腿、重复加仓和相关市场。
- **根因**：默认交易行独立同分布。
- **永久规则**：有效样本按独立事件、策略决策簇和时间阶段计算；fill 数只描述执行量。
- **验收**：事件聚类、按事件去一检验和阶段样本外结果必须随资格结论一起出现。

#### 从赢家排行榜发现，再用同一历史验证

- **对话表现**：主要从高 PnL 钱包中找候选，再用同一段历史说明其优秀。
- **根因**：发现集与验证集重合，产生赢家诅咒和多重筛选偏差。
- **永久规则**：保留搜索母集和淘汰记录；冻结候选与袖套规则后，用后续新数据验证。
- **验收**：报告披露扫描过多少候选、如何入选以及是否只是探索性结果。

#### 总 PnL、胜率和单一大单被混为长期正期望

- **对话表现**：用户后来才要求检查长期周期、单一大单贡献、前后阶段和最大回撤。
- **根因**：先看汇总结果，后检查收益来源。
- **永久规则**：每个钱包和袖套必须检查赔率价格、费用、事件级分布、最大事件贡献、去掉最大事件后的结果、连续亏损和阶段稳定性。
- **验收**：删除最大盈利事件后若翻负，只能标集中性假设，不得称稳定正期望。

#### 策略换挡处理太晚

- **对话表现**：用户主动指出“中间是否换过公式”后才开始讨论早晚阶段。
- **根因**：默认一个钱包等于一套固定策略。
- **永久规则**：先用领域、方向、价格、持有期、仓位和频率等事前行为特征识别变点，再评估阶段绩效。
- **验收**：变点不能由未来盈亏最优切分；当前阶段只使用变点后的证据并等待前瞻确认。

#### “专家袖套”可能事后挑赢家

- **对话表现**：要求剔除乱赌、只留专家部分是合理研究方向，但若看过结果后才定义袖套，会系统性美化。
- **根因**：分类边界使用结果泄漏。
- **永久规则**：袖套分类器只用标题、事件元数据和交易时点可见行为，在发现期冻结。
- **验收**：盲化盈亏后分类不变，后续新事件按冻结规则独立核算。

### 策略形态与复制能力

#### 把中途卖出当成不可跟

- **对话表现**：`ACTIVE_EXIT`、篮子和双向交易曾被挡在深度分析之外。
- **根因**：把“复杂”偷换成“不可复制”。
- **永久规则**：卖出只先描述为减仓、退出或反转；止盈、止损和观点更新是待检验机制。
- **验收**：生命周期不控制复制资格；排除必须引用我方执行或源经济性证据。

#### 过早确认做市、套利、速度模型或专家

- **对话表现**：从公开成交形态直接回答“完全是速度模型”“套利还是做市商”。
- **根因**：从相关行为推断不可观测意图。
- **永久规则**：机制标签分“观察事实”和“假设”；做市需要挂撤与库存证据，套利需要完整多腿锁价证据。
- **验收**：每个机制假设附无法观测项和会在未来出现的可证伪预测。

#### 把高频、做市、同秒成交和页饱和混成同一轴

- **对话表现**：旧扫描器曾用 `OBSERVABLE_MM_OR_SPEED` 合并策略机制、成交密度和 API 覆盖。
- **根因**：用一个标签代替多个不同问题。
- **永久规则**：分开记录订单角色、库存循环、成交密度、机会半衰期、覆盖截断和我方延迟结果。
- **验收**：页饱和只能产生 coverage 标记；同秒批量单边方向下注不能被称为做市。

#### 持有到结算不代表更差价格只减少利润

- **对话表现**：用户提出“方向对只是收益多少的问题”时，我没有立即指出同方向也可能因买价过高而从正期望变负期望。
- **根因**：把单次最终输赢与重复下注期望混淆。
- **永久规则**：所有持有到结算候选都用我方延迟 Ask 重算 edge。
- **验收**：源价为正、我方跟随价翻负的夹具必须阻止晋级。

#### 天气多选项和篮子被逐腿独立看待

- **对话表现**：早期偏向“新买新卖都能跟”，没有先判断多腿是否共同构成概率曲线、对冲或套利。
- **根因**：忽略腿间同步与权重。
- **永久规则**：组合收益按 basket 原子记录；缺任一关键腿都算组合复制失败。
- **验收**：账本有 basket ID、各腿发现时间、成交价格、缺腿状态和残余裸露风险。

#### “只要能跟，什么策略都可以”也需要红队

- **对话表现**：最新纠正方向合理，但不能由此忽略做市 maker 价格、跨价成本、逆向选择和套利多腿同步的先验困难。
- **根因**：修正误杀时可能过度纠偏。
- **永久规则**：策略类型不硬排除，但不同机制使用专属复制模型和不同研究优先级。
- **验收**：做市样候选展示源价差与我方跨价成本；套利样候选只有整组腿完成才计覆盖。

### 比例、最低量与资金

#### 用最小股数跟单破坏源仓位控制

- **对话表现**：初始纸面按每笔最低份数复制，用户指出源每笔金额不同体现仓位控制。
- **根因**：把“能下单”当成“风险暴露一致”。
- **永久规则**：按固定 share-scale 或冻结袖套权重缩放；最低量只决定成交、部分成交或跳过。
- **验收**：源仓位整体缩放时我方权重不变；不足最低量不得向上放大。

#### 建议攒到最低量再买，忽略价格已经消失

- **对话表现**：用户指出累计信号后价格可能早已变化。
- **根因**：为满足平台约束牺牲信号时点。
- **永久规则**：禁止跨时点拼接旧信号；只能固定比例成交、部分成交、明确跳过或重新作为新决策评估。
- **验收**：账本中不存在把多个旧动作合并成一个新价成交却仍算原信号跟单的记录。

#### 资金池、累计交易额、比例资金和预算答非所问

- **对话表现**：用户多次纠正“不是总共花了多少钱”“问的是金额”“不是一比一”“不是指定预算”。
- **根因**：计算前没有锁定被求变量和单位。
- **永久规则**：固定区分源袖套历史资金下界、最小固定比例、峰值并发占资、运营缓冲和用户指定纸面资金。
- **验收**：每个数字都给变量名、单位、公式、输入来源和未知项。

#### 正确公式使用了错误上游输入

- **对话表现**：极小 fill 导致比例和资金数量级异常。
- **根因**：下游算术正确掩盖上游“最小有效动作”未证明。
- **永久规则**：最小比例基于可验证逻辑净动作；无法恢复源订单边界时只能给敏感性与暂定覆盖测试。
- **验收**：改变单个 fill 碎片不得令资金结论数量级跳变。

#### 累计买入额被误称资金池，结算占资漏算

- **对话表现**：用户明确要求按买卖盈亏估算资金池并计入结算时间。
- **根因**：没有时间重放现金流。
- **永久规则**：历史资金下界取时间序列最大累计现金缺口，并计入费用、并发仓、卖出和实际资金释放。
- **验收**：总买入额变化但现金流路径不变时，资金下界不变。

#### 同比份数被误称同比风险

- **对话表现**：公开钱包总权益不可见，却逐渐把固定份数比例当成完整仓位控制复制。
- **根因**：忽略源账户现金、其它钱包、跨平台头寸和对冲。
- **永久规则**：明确写 share-scale、袖套权重或 equity-risk-scale；缺总权益时最后一种为 `BLOCK_DATA`。
- **验收**：任何“同比风险”结论都有源总权益证据。

### 工程、运行与网页

#### 先上线纸面，后决定找什么账户

- **对话表现**：账户资格、袖套和复制机制未定就启动纸面，后来用户指出顺序错误并要求停止删除。
- **根因**：把“有自动化在跑”误当研究进展。
- **永久规则**：没有 onboarding receipt 不创建正式运行时；确认纸面后才计算比例和上线。
- **验收**：启动脚本校验研究回执、袖套、比例、资金和数据覆盖。

#### 把代码完成当成生产上线

- **对话表现**：用户反复问是否有成交、会不会记账、网页是否自动；当前审计还发现天气纸面服务实际已停止。
- **根因**：验收停在单测、编译或 HTML，未跑真实 daemon 链路。
- **永久规则**：只有 OS 服务、公共 API、游标、决策、SQLite、状态文件和页面全部验证后才能说已上线。
- **验收**：服务真实 running、连续心跳前进、真实公共 GET 成功、错误为空、重启不重账。

#### 源动作没有不可变处理回执

- **对话表现**：用户看到源有动作却无法知道为什么纸面没有成交。
- **根因**：异常或跳过只写汇总错误，源动作可能在决策链中消失。
- **永久规则**：任何源动作先写 action receipt，再进入成交、部分成交、跳过、待处理或错误之一。
- **验收**：观察源动作总数等于各处理状态合计；每个交易哈希、token 和 side 可唯一追溯。

#### 游标和分页不足，存在静默漏单风险

- **对话表现**：旧实现只读最近一页并假设轮询足够快。
- **根因**：没有分页追到已处理边界，也没有 gap 阻断。
- **永久规则**：追不到游标边界时 `BLOCK_CURSOR_GAP`，禁止静默继续。
- **验收**：超过单页容量、停机恢复、重复页和乱序页测试做到不漏、不重或明确阻断。

#### 净仓快照被当成逐笔动作复制

- **对话表现**：天气跟单使用当前 positions；两次快照之间买入又卖出可能净仓不变，无法评价止盈止损是否跟住。
- **根因**：混淆目标净仓镜像与动作复制。
- **永久规则**：成交流驱动动作复制，仓位快照只用于对账和修正。
- **验收**：每个 BUY/SELL 有游标和回执；快照差异只产生告警，不伪造中间动作。

#### 轮询间隔被当成跟单延迟

- **对话表现**：只报多久扫一次，未拆源可见延迟、代理、盘口查询和记账。
- **根因**：用配置替代端到端实测。
- **永久规则**：记录源时间、API 首次可见、本机发现、盘口时间和记账时间。
- **验收**：按真实样本报告延迟分布；无样本时明确不能计算。

#### 网页刷新被当成服务持续运行

- **对话表现**：浏览器可以自动刷新旧 HTML，即使 daemon 已死。
- **根因**：数据生产者健康与页面刷新混在一起。
- **永久规则**：页面根据当前时间自动识别心跳过期并显示故障。
- **验收**：停止 daemon 后页面无需唤醒 Codex 就自动变为陈旧状态。

#### 账务与状态页首版不完整

- **对话表现**：上线后用户才逐项要求已实现盈亏、可用现金、占用资金、持仓中、待结算、已结束和单笔盈亏。
- **根因**：首版围绕进程设计，不是围绕账户账本设计。
- **永久规则**：资金表、持仓三态和已关闭逐笔盈亏是首版验收条件。
- **验收**：账户恒等式、单笔合计与账户累计、重启重放全部一致。

#### 只修点名服务，没有全量检查兄弟服务

- **对话表现**：Tian-Wen 后来修复了解释器和代理问题，天气服务仍保留旧配置并在当前审计中失败。
- **根因**：修具体账号，没有修 daemon 部署合同。
- **永久规则**：启动器、代理、解释器、心跳、游标、账务和页面改动都对全部同类服务运行矩阵检查。
- **验收**：自动列出所有服务并逐项报告，不允许用一个正常服务代表全部正常。

#### 每日自动找钱包的承诺没有真正实现

- **对话表现**：用户明确要求每天定时找新账户；当前只有一次性扫描器和手工报告。
- **根因**：把一次执行和持续调度混为一谈。
- **永久规则**：持续任务必须有真实 OS 调度、持久状态、失败记录和上次/下次运行信息。
- **验收**：关闭 Codex 后仍会按计划执行，失败不覆盖已有候选池。

### 沟通与交付

#### 没有先回答用户真正问的对象

- **对话表现**：用户追问钱包地址、网页、金额、是否成交、资金池含义和术语。
- **根因**：先展示过程和内部状态，后回答结果。
- **永久规则**：首句直接回答对象和单位，再补依据。
- **验收**：删掉解释后，首句仍能独立回答本轮问题。

#### 内部术语直接暴露

- **对话表现**：`FORMULA_RESEARCH`、净仓位箭头和其它内部标签让用户重复追问。
- **根因**：用实现语言替代业务语言。
- **永久规则**：每个内部枚举同时给中文、为何重要和行动含义。
- **验收**：用户不读代码也能看懂状态页和报告。

#### 钱包交付缺地址与验证入口

- **对话表现**：用户连续要求“钱包地址”“网页”“策略和网页地址”。
- **根因**：分析结论替代了可操作交付。
- **永久规则**：候选模板固定包含完整地址和可点击页面。
- **验收**：用户无需再次追问即可自行打开核查。

#### 只修点名例子，没有修全类

- **对话表现**：先只分析 tetrose，后来才把生命周期要求推广到所有钱包；结束时间、账务字段和服务配置也经历逐项补丁。
- **根因**：锚定用户点名对象。
- **永久规则**：每次纠正先升维到同类，修改通用合同、所有实例和反例测试。
- **验收**：抽查未被点名的另一个钱包或页面，也具有同样行为。

#### 完成声明缺少即时证据

- **对话表现**：用户反复问现在是否成交、是否会记账、是否自动运行。
- **根因**：把做过动作与可验证完成混为一谈。
- **永久规则**：声称完成、上线、运行或修复时附本轮即时状态、页面、时间和关键输出。
- **验收**：第三方无需相信口头保证即可复核。

## 后续强制验收钩子

以后处理任意新钱包时，交付前必须能够回答：

- 我究竟看到了哪些公开事实，哪些数据不可见？
- 我对策略机制的解释有哪些替代假设？
- fill、交易、逻辑动作、事件和策略阶段是否分开？
- 源策略是否有去集中、去结果泄漏和阶段样本外证据？
- 我方在延迟 Ask/Bid、深度、费用和最低量后是否仍有经济性？
- 固定比例和资金是否由可验证动作、并发占资和结算重放得到？
- 每个源动作是否都有唯一纸面回执？
- daemon、游标、账本、状态文件和页面是否都在真实生产环境健康？
- 用户是否无需再次追问地址、网页、金额、状态和错误原因？
- 本轮修复是否已经覆盖所有同类实例，而不是只覆盖点名对象？

只有全部相关问题都有证据，才能使用“已分析”“可纸面验证”“正在运行”或“已完成”等结论。
