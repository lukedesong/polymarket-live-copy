# Tian-Wen 链上快速影子通道设计

## 目标

在不修改现有 Tian-Wen 纸面账户、持仓、余额和历史账本的前提下，新增一个独立只读通道，直接观察 Polygon 上 Polymarket Exchange 的 `OrderFilled` 日志。它与现有 Data API 通道并行记录同一源成交，量化：

1. 区块成交到链上观察的延迟；
2. 区块成交到 Data API 首次观察的延迟；
3. 两个观察时点各自对应的完整 CLOB 盘口；
4. 延迟改善能消除多少价格损耗；
5. 剩余价格变化是否属于成交后的客观市场重定价。

本通道只生成研究记录，不提交、签名、撤销或模拟记入现有纸面账户的订单。

## 已确认根因

- 现有 tracker 的 `source_timestamp` 是源成交所在 Polygon 区块的时间。
- 当前样本中的源成交已经能从链上回执的 `OrderFilled` 日志识别源钱包。
- 现有 Data API 通道把配置的休眠间隔显示成扫描频率，但端到端循环还包括网络请求、结算轮询和页面渲染。
- 当前执行损耗的主要组成是源成交后盘口变化，费用只占较小部分。
- 是否能通过链上通道保住原价格必须用新的前瞻盘口快照验证，不能用历史成交价或当前盘口倒推。

## 方案

### 1. 独立进程与独立数据

新增 `tian_wen_chain_shadow.py`，使用单独的 runtime 目录和 SQLite 数据库。现有 `tian_wen_speech_paper.py`、`tian_wen_speech_runtime/paper.sqlite3` 和现有 LaunchAgent 保持不变。

新进程写入：

- `chain_events`：区块、交易、日志、源钱包角色、Token、方向、数量、价格和链上首次观察时间；
- `book_snapshots`：链上首次观察后立即取得的完整 bids/asks、盘口时间戳、请求开始和完成时间；
- `data_api_matches`：同一交易在 Data API 首次出现的时间和原始字段；
- `runtime_state`：心跳、真实循环耗时、最后处理区块、错误和安全标记。

所有主键使用链 ID、交易哈希和日志序号，重启后幂等，不重复记账。

### 2. 链上观察

使用只读 Polygon JSON-RPC：

- 读取最新区块；
- 从持久化的最后完成区块继续；
- 查询 Polymarket CTF Exchange 与 Neg Risk Exchange 的 `OrderFilled`；
- 过滤 maker 或 taker 为 Tian-Wen 源钱包的日志；
- 解码 Token、方向、成交数量、成交金额、费用和源成交价。

首次启动只设置区块水位，不回放并伪装成前瞻记录。若发生进程中断，可补齐水位之后的区块，但补齐记录必须标记为 `catchup=true`，不得与实时延迟样本混合。

### 3. 策略范围识别

链上日志只提供 Token 与成交信息。为了不因元数据查询而错过第一时点盘口，
通道先对源钱包的每个新 `OrderFilled` 立即保存盘口，再异步维护 Token 元数据缓存：

- 优先使用已经存在的 Tian-Wen source state；
- 不足时只读查询 CLOB/Gamma 元数据；
- 仅 Trump 说词市场进入最终 A/B 统计；
- 无法及时确认范围的事件先保存盘口并标记为 `scope_pending`，后续补充元数据，
  不能丢失链上原始记录或第一时点盘口。

### 4. 盘口快照

每个新的范围内链上成交被观察后，立即读取该 Token 的完整 CLOB book，并保存原始深度。记录以下时间：

- `block_timestamp`；
- `chain_seen_at_ms`；
- `book_request_started_at_ms`；
- `book_request_finished_at_ms`；
- CLOB 返回的 `book_timestamp`。

不把 CLOB 的最后更新时间冒充请求完成时间。

### 5. Data API 对照

独立线程持续读取公开用户成交：

- 以交易哈希、Token 和方向匹配链上事件；
- 记录 `data_api_seen_at_ms`；
- 保存 Data API 数量、价格与时间；
- 对数量碎片进行交易级汇总，但保留原始行；
- 计算链上观察延迟、Data API 延迟和两者差值。

### 6. 不追价研究

本阶段不设任意滑点阈值，也不修改现有纸面成交。保存完整盘口后，可在结算时对任意价格保护规则进行离线计算，避免把未经验证的阈值写成可执行参数。

## 安全边界

- `paper_only=true`
- `real_order_submitted=false`
- 无私钥、L1/L2 凭证或下单客户端依赖
- 公共 GET/JSON-RPC 只读
- 新数据库与旧纸面数据库隔离
- 启动、停止、重启均不影响现有纸面账户
- RPC 故障、区块缺口或解码不确定时写入阻塞状态，不猜测成交

## 错误处理

- RPC 不可用：保留最后完成区块，指数退避后续继续；
- 区块缺口：停止实时统计，先按区块顺序补齐并标记 catch-up；
- 链重组：在确认深度内重新核对区块哈希，撤销孤块记录；
- 元数据缺失：保留原始事件并标记 pending；
- 盘口失败：记录失败原因和请求时间，不生成虚构价格；
- Data API 未匹配：事件保持待匹配，不影响链上记录。

## 测试标准

### 单元测试

- 正确解码 BUY 与 SELL 的 V2 `OrderFilled`；
- maker、taker 两种源钱包角色都能识别；
- 非目标钱包日志被排除；
- 交易哈希加日志序号幂等；
- 元数据范围过滤与 pending 行为正确；
- 延迟只使用真实观察时间，不使用 book 的最后更新时间；
- catch-up 样本不会进入实时延迟统计；
- 任一安全标记都保持无真实订单路径。

### 历史回执集成测试

用已经写入旧账本的交易哈希读取链上回执：

- 区块时间与旧账本 source timestamp 一致；
- 能找到源钱包对应的 `OrderFilled`；
- 解码价格与 Data API 源价格一致；
- 解码数量与对应公开成交汇总一致。

### 运行验证

- 新 LaunchAgent 单实例运行；
- SQLite integrity check 通过；
- 心跳持续更新；
- last processed block 单调递增；
- 页面或状态 JSON 明示只读影子与无真实订单；
- 新进程只以 SQLite 只读 URI 打开旧纸面数据库，且代码与测试证明不存在旧库写入路径；
- 启动前后核对旧库余额、持仓和账本。若旧 daemon 在核对窗口内产生自己的合法更新，
  以写入来源审计区分，不能把文件哈希变化直接归因于新通道。

## 验收结论

启动后先积累新的前瞻链上事件。只有同一交易同时具备链上首次盘口和 Data API 首次盘口，才能量化可修延迟带来的价格改善。若链上首次盘口已经失去源价格，则该部分归为成交后客观不可复制；若链上盘口仍保留而 Data API 盘口已明显恶化，则确认慢数据源是可修主因。
