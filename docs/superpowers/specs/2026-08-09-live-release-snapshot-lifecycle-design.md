# 发布快照生命周期设计

## 目标

保留一次发布尚未完成时所必需的本地回滚能力；成功发布后自动清理该次快照，避免成功发布不断复制生产账本并耗尽系统盘。失败发布保留快照和失败证据，供现有回滚逻辑与事后审计使用。

## 已确认事实

- 发布脚本在停止提交服务后，为 CD90、网球和共享钱包账本创建本次发布的 SQLite 备份，并保存相关 systemd 文件。
- 回滚函数仅在 `committed=0` 时使用该次快照；新服务已被允许提交后，脚本不会自动恢复账本。
- 当前脚本在服务重新启动并确认 `active` 后设定 `committed=1`、解除回滚 trap，却没有删除本次快照。因此已成功的历史发布快照会无限积累。
- 当前服务器没有可核验的 Polymarket 独立定时备份；本设计不把同一系统盘上的快照冒充为灾备。

## 决策

采用“成功即自动清理、失败保留”。这里的“成功”是发布脚本自身已完成以下不可变边界：

1. 候选发布已切换为 `/opt/polymarket-live/current`；
2. CD90 与网球服务均已由 systemd 确认 `active`；
3. 脚本将本次事务标记为 `committed=1`。

只有在这些条件完成后，脚本才会删除**本次命令传入的精确 snapshot 路径**。该删除不使用目录通配符，也不按定时器扫描历史目录。

## 失败语义

- 在 `committed=1` 前任一步失败：保留快照，沿用现有 rollback trap；若回滚本身失败，也保留快照和原始错误。
- 新服务开始后出现不确定提交状态：沿用现有 fail-closed 行为，禁止用删除快照掩盖账本或订单问题。
- 自动清理失败：发布结果不能被改写为失败，也不能重跑删除；记录精确快照路径和删除错误，留待人工处理。

## 明确不处理的对象

- `cd90_live`、`tennis_live` 和 `shared_wallet` 的当前运行目录；
- 任意 SQLite 主库、`-wal`、`-shm` 文件；
- 当前发布版本、历史 release、归档文件或环境凭证；
- 任何非本次事务传入的快照目录。

## 审计与可观测性

成功清理必须输出结构化回执，包含本次 snapshot 路径、发布变更标识和终态 `SNAPSHOT_PRUNED_AFTER_COMMIT`。失败发布继续保留 snapshot 路径作为现有失败/回滚证据。

长期灾备是独立课题：只有配置到不同故障域的存储并完成恢复验证后，才能称为备份；在此之前，不保留成功发布的系统盘快照作为伪灾备。

## 测试与验收

- 回归测试证明清理语句位于服务 `active` 检查、`committed=1` 和 rollback trap 解除之后。
- 回归测试证明 rollback 函数中不存在快照删除。
- 回归测试证明清理目标仅能是脚本参数中已通过路径校验的 snapshot，不能由 glob 或目录扫描生成。
- 部署后即时核验：当前发布链接正确、两项服务 `active`、当前运行账本存在、该次 snapshot 不存在、系统盘容量回升。
- 若任一验收失败，保留快照和原始证据，不改写账本、不重新提交订单。
