# 源动作完整复刻与篮子不漏腿设计

## 1. 用户确认与目标函数

本设计适用于共享真实跟单核心中的“已被对应 profile 判定为可跟随”的源动作。

用户在 2026-08-07（上海时间）明确确认：

1. 跟单系统的 P0 是尽可能完整地复刻源钱包的全部可跟随 BUY/SELL 动作；
2. 不要求单笔、单腿、单篮子或任意阶段单独为正期望；
3. 不因组合漂移、单腿价格或某个篮子亏损而暂停开启新篮子；
4. 源钱包持续产生动作时，系统持续跟随；漂移、费用和剩余 edge 只用于监控、复盘与是否继续授权该源钱包，不充当逐动作下单闸门。

因此，执行优化目标按以下优先级排序：

1. 保持源动作身份、方向、先后顺序和固定 share-scale；
2. 消除由我方代码、状态机、重启、最低量处理或 FAK 零成交处理造成的可避免漏腿；
3. 在真实市场物理约束下尽快取得可验证成交；
4. 完整记录复制损耗，但不按单腿盈利性筛选源动作。

“尽可能完整”不是承诺市场永远有对手盘。无法由代码消除的约束包括：市场已关闭或结算、整个允许盘口没有可成交深度、账户真实抵押品不足、源 SELL 对应的我方库存为零、官方接口持续不可用。此类情况必须保留为非成功终态或待处理状态，不能伪造成交，也不能归入内部正常跳过。

## 2. 当前缺陷及根因

当前共享核心逐动作规划和终态化，缺少事件级持久状态：

- 比例数量低于市场最低量时，部分 profile 直接写入永久 `SKIPPED`；
- FAK 被取消或零成交时，对应动作被写入永久 `SKIPPED`；
- 账本没有 `event_slug` 决策单元、篮子动作集合、未完成腿和重试状态；
- 游标可以在某条腿永久跳过后继续推进，页面只能看到动作失败，不能证明篮子完整；
- 漂移分析与执行状态没有正式分离，容易再次把监控数字误用为单腿过滤条件。

这些是我方执行状态机缺陷，不是源策略亏损，也不是不可抗力。

## 3. 不采用的方案

### 3.1 单腿价格上限

拒绝。单腿或单篮子可以正常亏损。把单腿漂移与历史平均比较会系统性漏掉价格较差的后续腿，改变源钱包的动作分布。

### 3.2 每次下单前检查组合损耗预算

拒绝作为订单闸门。即使使用美元周转加权，只要它能阻止下一腿或下一个篮子，仍然会改变源动作序列。组合损耗可以触发告警和人工重新评估源钱包，但不能静默改变当前已授权的复制合同。

### 3.3 首腿成交后才承诺完成该篮子，并在篮子边界暂停

拒绝。用户明确要求不存在“暂停开启新篮子”；源钱包产生可跟随动作时继续跟随。

## 4. 采用的方案：Eligible Action Fidelity 状态机

### 4.1 动作与决策单元身份

动作的不可变身份继续使用：

`transaction_hash + token_id + side + order_hash`

每个动作在任何规划或提交前必须解析并冻结：

- `condition_id`；
- `market_slug`；
- `event_slug`；
- profile eligibility 决定及其元数据哈希；
- 源时间、发现时间、区块号和区块哈希。

天气等多市场篮子的决策单元使用 `event_slug`。单一二元市场仍保留 `condition_id`，但也必须绑定其唯一 `event_slug`。官方元数据暂时不可得时，动作进入 `PENDING_METADATA`，不得下单、不得推进为永久跳过、不得用后来盘口伪造旧成交。

### 4.2 动作状态

每个可跟随动作只能处于下列业务状态之一：

- `OBSERVED`：链上动作已冻结；
- `PENDING_METADATA`：等待官方市场/事件身份；
- `READY`：身份、比例、现金与当前盘口已取得；
- `SUBMITTED_UNRECONCILED`：真实订单已提交，等待权威成交对账；
- `PARTIAL_PENDING`：已有部分真实成交，剩余目标仍待复制；
- `PENDING_LIQUIDITY`：当前 FAK 零成交或当前盘口不足，等待新盘口重试；
- `PENDING_MINIMUM_UNWIND`：SELL 可用库存低于市场最低量，当前无法合法卖出；
- `PENDING_CAPITAL`：BUY 所需真实现金当前不足；
- `FILLED`：目标数量已完成；
- `EXTERNAL_UNFILLABLE`：市场关闭、结算或经官方状态证明不可再成交；
- `SUPERSEDED_UNFILLED`：较早动作从未成交，且后续相反源动作使迟到执行会颠倒源钱包净动作；
- `ERROR_INTERNAL`：我方不变量、账务、解码或持久化错误，必须停留并报警，不能被巡检重启覆盖。

`SKIPPED` 仅保留给 profile 明确排除的动作，例如一个只授权赛前主盘的 profile 收到赛后或非主盘动作。CD90 全钱包 profile 没有逐腿盈利筛选，因此最低量、价格漂移、FAK 零成交和单腿亏损均不得成为 `SKIPPED` 原因。

### 4.3 BUY 规划

BUY 的基础目标保持固定比例：

`proportional_quantity = source_quantity × fixed_share_scale`

其中 fixed share-scale 使用现有不可变 scale receipt；增加备用现金不得修改比例。

若基础目标低于当前市场最低股数或最低可成交金额，则本次请求量为：

`requested_quantity = max(proportional_quantity, market_minimum_shares, minimum_marketable_notional / current_ask)`

这是由当前市场外部约束推导的最小可执行数量，不是新的策略比例。账本必须同时保留基础目标、实际请求量和由最低量造成的超额数量，供组合权重偏差复算。

若当前现金不足，请求不得伪造成交或永久跳过；状态为 `PENDING_CAPITAL`。现金恢复后，使用新盘口重新规划。现金不足属于真实资源约束，但若共享钱包协调器误算可用现金，则属于 `ERROR_INTERNAL`。

### 4.4 SELL 规划

SELL 目标仍为源数量按固定比例缩放，但最多只能卖出我方对应 token 的实际可用库存，禁止卖空。

- 有足够库存且达到市场最低量：提交 FAK；
- 有库存但低于最低量：`PENDING_MINIMUM_UNWIND`，不向上卖出超过库存；
- 完全没有库存：若源 BUY 发生在本跟单水位之前，记为可解释的 `EXTERNAL_UNFILLABLE_NO_PREWATERMARK_INVENTORY`；若源 BUY 在水位后却因我方内部故障缺失，则为 `ERROR_INTERNAL_MISSING_PRIOR_BUY`。

### 4.5 FAK 零成交、部分成交与重试

FAK 仍是当前真实立即成交订单类型，但它只是一次成交尝试，不是源动作的业务终态。

- 零成交或官方取消：释放本次预留，动作进入 `PENDING_LIQUIDITY`；
- 部分成交：先用权威成交回执入账，未完成数量进入 `PARTIAL_PENDING`；
- 下一次可用新盘口到达时，按“原目标减去累计权威成交量”重新提交；
- 每次提交有独立 attempt id、订单 id、盘口快照和权威成交回执；
- 重启后先对账所有 `SUBMITTED_UNRECONCILED`，只有证明未成交后才能重试；
- 禁止对结果未知的订单重复提交。

不设置拍脑袋的重试次数或固定秒数。重试终止只依据可验证状态：目标完成、市场正式不可交易、动作被后续相反源动作因果性取代、或真实资源约束持续存在。

### 4.6 因果顺序与相反动作

同一 token 的动作按源区块、源时间、交易哈希和订单哈希排序。较早 BUY 完全未成交，而后续源 SELL 已出现时，继续在 SELL 之后补买会颠倒源钱包净动作，因此较早未成交 BUY 转为 `SUPERSEDED_UNFILLED`；SELL 再按我方实际库存处理。

已有部分成交的 BUY 不能简单删除：已成交部分保留，后续 SELL 先作用于实际库存；未成交剩余量由净动作折抵，并留下精确计算回执。

## 5. 篮子完整性账本

新增事件级持久表，至少保存：

- `event_slug` 与元数据哈希；
- 首次/最后源动作时间；
- 观察到的可跟随动作数；
- FILLED、PARTIAL/PENDING、EXTERNAL_UNFILLABLE、ERROR_INTERNAL 数量；
- 每条腿源数量、比例目标、累计成交、未完成量；
- 事件当前暴露与完整率；
- 市场关闭/结算状态。

动作守恒公式：

`eligible_observed = filled + partial_or_pending + external_unfillable + internal_error`

上式任何时刻不成立都属于内部账本错误。不能只统计成交动作，也不能把 fill 碎片冒充源动作。

页面和健康报告新增：

- 可跟随源动作复刻率；
- event_slug 篮子完整率；
- 当前未完成腿及原因；
- 内部漏腿数；
- 外部不可成交腿数；
- 最旧 pending 年龄；
- 每个动作的源价格、我方成交 VWAP、价格损耗、费用和总执行拖累。

## 6. 漂移与 edge：只监控，不拦单

监控必须使用美元周转加权，不能平均事件百分比：

`price_loss = Σ scaled_quantity × adverse(follower_vwap - source_price)`

`total_execution_drag = price_loss + actual_follower_fees`

`weighted_price_drift = price_loss / source_scaled_turnover`

当前 CD90 历史研究参考值：

- 官方关闭天气篮子：394 个，属于实证样本量；
- source PnL：3,289.520487 USD，属于官方公开数据全分页后的实证值；
- source turnover：10,900.684591 USD，属于公式重放值；
- 同价跟随费用估算：253.323809 USD，属于按官方天气费率公式推导值；
- 价格损耗 break-even 点估计：
  `(3,289.520487 - 253.323809) / 10,900.684591 = 27.8533%`，属于公式推导值。

独立复核确认：上述旧复算使用内存中的实时官方 API 响应，没有保存完整分页 raw、精确 cutoff、规范化输入 bundle 或 SHA256。旧截止时间只能恢复到近似时刻，不能冒充精确冻结时间。因此该值进一步降级为 `MONITORING_REFERENCE_UNREPRODUCED`。它不得进入下单函数、不得导致 `SKIPPED`、不得暂停下一个篮子，也不得被描述成已冻结生产参数。若监控显示整体复制经济性恶化，只能生成带完整分母和来源的重新评估报告；改变 profile 授权必须由用户另行明确决定。

页面若显示该历史研究值，必须同时显示“原始快照、精确截止时间和输入哈希缺失”。若以后需要升级证据，必须重新冻结完整分页 raw、精确 cutoff、Gamma/CLOB 关闭状态、规范化输入 bundle、SHA256 和可重放计算 receipt；即使完成升级，它仍只能监控，除非用户另行明确改变执行合同。

## 7. 迁移与发布

本次迁移必须是前向、可回滚且不重写历史：

1. 不修改既有 action receipt、成交、现金、持仓、成本、已实现盈亏和 scale；
2. 只增加新表/新列，并为部署后的新动作启用新状态机；
3. 历史 `SKIPPED` 继续作为历史事实展示，不改写成成功；
4. 当前已存在且结果未知的真实订单必须先权威对账；
5. 发布时使用共享钱包锁，同时停住受影响服务，备份数据库，迁移副本验证后再迁移正式库；
6. 任一步失败，恢复旧 release 和原数据库；
7. 新 release 启动后核验每个 profile 只有一个 daemon、游标追平、SQLite integrity_check、动作守恒、协调器现金守恒和真实安全旗标；
8. 不手工补下部署前缺失的旧腿，因为不存在其当时可执行盘口。

## 8. 测试合同

实现前必须先加入会失败的回归测试：

1. CD90 比例 BUY 低于市场最低量时按当前外部最低量提交，不再 `SKIPPED`；
2. FAK 零成交进入 `PENDING_LIQUIDITY`，新盘口后重试且不会重复提交未知订单；
3. 部分成交只重试剩余量，累计成交不超过目标；
4. 单腿或整个篮子漂移超过监控参考值仍继续提交；
5. 新 event_slug 不因组合漂移参考值而暂停；
6. metadata 暂时不可得时游标可安全重放，且不会丢动作；
7. 重启后 pending 腿恢复，attempt/order id 幂等；
8. 较早未成交 BUY 遇到后续 SELL 时不会在 SELL 后错误补买；
9. SELL 无库存区分水位前缺仓与内部漏掉先前 BUY；
10. 多 profile 共用一个真实钱包时，现金、订单锁、token/condition 归属和动作账本不串账；
11. 数据库迁移前后既有现金、持仓、PnL、成交行和 scale 完全相等；
12. 状态页可复算动作守恒、篮子完整率和执行拖累；
13. 任何内部异常不会被巡检重启覆盖为健康；
14. 完整测试通过后才允许生成发布包。

## 9. 验收标准

发布完成不能只凭进程启动。必须同时取得：

- 本地完整测试通过；
- 发布包与服务器当前文件哈希一致；
- 数据库 `integrity_check` 通过；
- 每个 live profile 恰好一个进程；
- 心跳新鲜且链游标追平；
- 源动作守恒成立；
- 所有部署后 eligible 动作没有因价格漂移、单腿盈亏、最低量或 FAK 零成交被永久 `SKIPPED`；
- pending 腿有最新尝试或明确资源/外部约束；
- 共享钱包现金、预留与持仓守恒；
- 真实订单仍仅由已授权 live profile 自动提交，不产生人工测试订单。

如果观察窗口内源钱包没有新动作，只能报告该窗口 `N=0`，不能把静默期当作新状态机成交路径已经实证通过。
