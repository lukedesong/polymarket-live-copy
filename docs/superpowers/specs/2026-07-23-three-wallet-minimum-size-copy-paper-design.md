# 三钱包最小股数跟单纸面追踪设计

## 目标与边界

持续观察三个已确认的公开 Polymarket 钱包，并为每个钱包维护一个完全独立的纸面账户。钱包出现新的买卖成交后，系统按对应市场当时的官方最小下单股数模拟一次跟随成交，最终分别核算三个账户的现金、持仓和输赢。

这是观察性纸面实验，不是实盘复制交易：

- 不读取私钥、API 密钥或签名材料；
- 只允许访问公开只读接口；
- 不实例化认证交易客户端；
- 不调用创建、取消或修改订单的接口；
- 所有状态和报告都明确写入 `paper_only: true` 与 `real_order_submitted: false`。

## 数字与对象来源

### 用户指定值

- 三个独立账户，每个账户初始纸面现金为 **100 USD**。这是用户指定的实验资金，不代表已验证最优资金量。
- 跟踪对象为此前筛选并由用户确认的三个钱包：
  - `russell110320`：`0x118689b24aead1d6e9507b8068d056b2ec4f051b`
  - `ZorroDeLaVega`：`0xaae9b2c5ad90e82b5068c7f8a4b491997633d661`
  - `sabsabinxz`：`0xd3ecb2aee0d65622da559ff356b00e8c2e626603`
- 三个账户互不借款、互不调拨现金、互不净额结算。

### 外部约束值

- 每次纸面订单的数量来自本次下单前 CLOB 订单簿响应中的 `min_order_size`，不得使用测试夹具或历史市场的固定值。官方说明见 [Get order book](https://docs.polymarket.com/api-reference/market-data/get-order-book)。
- 价格刻度、市场状态、费用参数和结算结果同样读取当时的官方公开数据。
- 轮询调度必须低于官方接口限制，并在节流或服务错误时退避；不得把旧守护进程中的等待时长当成合理默认值。官方限制见 [Rate Limits](https://docs.polymarket.com/api-reference/rate-limits)。

### 实证值

- 钱包地址与公开用户名来自本轮钱包筛选时的公开资料查询；实现前用公开资料接口再次校验地址与用户名对应关系。
- 每次源成交、订单簿快照、费用输入和结算结果都连同抓取时间及原始字段写入审计账本，纸面成交只能由这些实证记录产生。

## 数据来源

系统仅使用公开 GET 请求：

- Data API `/trades`：按钱包读取成交，显式设置 `takerOnly=false`，同时覆盖该钱包作为 maker 或 taker 的公开成交。该参数默认只返回 taker，因此不得依赖默认值。字段和分页约束见 [Get trades for a user or markets](https://docs.polymarket.com/api-reference/core/get-trades-for-a-user-or-markets)。
- CLOB `/book`：读取目标 token 的即时买卖深度、`min_order_size`、`tick_size`、订单簿时间和哈希。订单簿是公开端点，不需要认证，见 [Orderbook](https://docs.polymarket.com/trading/orderbook)。
- Gamma/CLOB 公开市场资料：核验市场是否仍可交易、费用参数及最终结算结果。

网络层使用明确的主机、HTTP 方法和路径白名单。任何非 GET 请求、认证头或交易路径都直接拒绝并记为安全错误。

## 启动水位与源成交识别

首次启动时记录一个启动水位。启动水位以前及等于水位的历史成交只用于建立去重基线，不生成纸面订单；只跟随水位之后首次观察到的新成交。

每轮拉取后先规范化并排序，再以以下字段构造源动作身份：

`wallet + transactionHash + asset + side`

同一链上交易中，同一钱包、token 和方向的多个成交行合并成一个源动作，防止一个被拆分撮合的订单触发多次最小股数跟单；同一交易中不同 token 或不同方向仍分别处理。原始成交行全部保留，以便复核合并是否正确。

上述合并方式是用户确认的实验规则，不代表 Data API 提供了源订单 ID。若同一链上交易确实包含多个同 token、同方向的独立源订单，它们会被合并为一个跟随信号；报告必须披露这一识别限制。

Data API 成交时间、CLOB 订单簿时间与本机观察时间先转换到同一 UTC 时间单位再比较，原始值和原始单位同时保留。无法可靠识别时间单位时停止该次纸面动作，不能靠数值大小猜测。

检查点只有在源动作及其纸面结果已经原子落账后才前移。重启后重新读取同一批数据时，唯一约束保证不会重复跟单。

## 纸面成交规则

### BUY 源动作

1. 读取该 `asset` 的新订单簿快照。
2. 将纸面数量设为本次快照的 `min_order_size`。
3. 从最低卖价开始逐档消耗可见卖盘，必须让全部数量可立即成交。
4. 按各档真实数量计算成交金额，并加入官方费用。
5. 只有该账户可用现金足以覆盖完整成本时才纸面成交。

源钱包的历史成交价只作为源信号证据，不作为我们的成交价。这样会真实保留发现延迟、价差和盘口移动造成的跟单成本。

### SELL 源动作

1. 读取该 `asset` 的新订单簿快照和当前 `min_order_size`。
2. 若该账户持仓不少于当前最小股数，则从最高买价开始逐档卖出一个最小股数，并扣除官方费用。
3. 若没有该 token 持仓，则记录 `SKIP_NO_POSITION`。
4. 若剩余持仓低于当前官方最小股数，则记录 `SKIP_BELOW_MINIMUM`，不虚构低于交易所最小量的主动卖出；该余量继续持有至后续满足卖出条件或市场结算。

每个源 BUY 或 SELL 动作最多触发一个最小股数纸面动作。连续的源 BUY 可以逐次累积持仓；连续的源 SELL 也只能逐次减少实际持有的纸面仓位。

### 共同拒绝条件

出现以下任一情况时不产生纸面成交，而是保存证据和明确原因：

- 市场已关闭、暂停或不再接受订单；
- 缺失最小股数、费用或必要的市场约束；
- 订单簿时间早于源成交时间、时间倒退或快照身份不一致；
- 可见深度不足以完整成交一个最小股数；
- BUY 的完整成本超过该账户可用现金；
- SELL 的实际持仓不足；
- 官方接口异常、节流或返回无法校验的数据。

纸面动作采用全量立即成交或完全跳过，不制造部分成交，也不使用中间价、最后成交价或未来数据补成交。

## 账户与盈亏

一个 SQLite 审计库保存三个逻辑账户，但所有账户表都以 `account_id` 分区，并以数据库约束禁止跨账户使用现金或持仓。单库便于统一去重和生成总览，不改变三个账户资金完全独立的事实。

每个账户至少维护：

- 初始现金、可用现金和累计费用；
- 按 token 区分的股数和 FIFO 成本批次；FIFO 只是已实现盈亏的会计展示规则，不改变账户总现金流；
- 已实现盈亏、已结算盈亏；
- 按当前可见买盘深度计算的可执行清算价值；
- 无法由当前深度卖出的剩余数量；
- 总权益及相对初始现金的纸面盈亏。

开放持仓的展示盈亏不是最终输赢。市场正式结算后，系统读取官方结果，按官方合约兑付规则结算持仓，释放现金并写入不可变结算记录。最终账户输赢以现金和所有已结算现金流为准；未结算账户同时报告可执行清算口径，不能把中间价标记当成可实现利润。

## 持续运行与恢复

使用一个只读后台进程同时观察三个钱包。进程包含：

- 单实例锁，防止重复守护进程消费同一信号；
- 原子检查点和数据库事务，保证崩溃后可恢复；
- 自适应轮询，在官方限制内运行，对节流、匹配引擎重启和服务错误执行退避；
- 明确的停止标记，人工停止后监督程序不得自动复活；
- 心跳状态，记录最近成功抓取、最近源动作、最近纸面动作和最后异常；
- 结构化日志，保留原始请求时间、响应身份、决策理由和账本前后余额。

连续运行不等于连续伪造数据。接口不可用期间只记录数据缺口；恢复后可以识别缺口期间的新源成交，但只能使用恢复时的新订单簿模拟跟单，并把实际发现延迟写入结果。

## 可查看输出

本地状态页按钱包分成三个账户卡片，展示：

- 运行状态和最后更新时间；
- 纸面现金、持仓、可执行权益、已实现及已结算盈亏；
- 最近的源成交与对应纸面成交或跳过原因；
- 累计源动作数、纸面成交数和各类跳过数；
- `paper_only` 与 `real_order_submitted` 安全标记。

同时导出可复核的逐笔 CSV。网页和 CSV 都只读取 SQLite 审计库，不维护第二套账本。

## 测试与验收

实现阶段遵循测试先行。至少覆盖：

- 三个账户初始现金相同但余额、持仓和盈亏互不污染；
- 首次启动不回补历史交易；
- `takerOnly=false` 被显式发送；
- 同一交易的拆分成交只产生一个最小股数动作；
- 同一交易中的不同 token 分别处理；
- BUY 按当时 `min_order_size` 和可见卖盘逐档成交；
- SELL 按当时 `min_order_size` 和可见买盘逐档成交；
- 资金不足、深度不足、无持仓、低于最小股数和陈旧数据均正确跳过；
- 重启和重复响应不会重复成交；
- 正常结算和异常结算数据不会错误入账；
- 任意网络调用都不能越过只读 GET 白名单；
- 状态与逐笔导出可由数据库重新生成并与账本对平；
- 启动短时真实公开数据验证后，所有状态仍为 `paper_only: true`、`real_order_submitted: false`。

验收时还要检查进程唯一性、数据库完整性、三个账户的现金恒等式、源动作到纸面结果的一一映射，以及人工停止后没有监督进程将其重新拉起。

## 明确不做

- 不复制源钱包历史仓位；
- 不按源钱包仓位比例缩放；
- 不以源钱包成交价假装同步成交；
- 不为了凑成交而降低官方最小股数；
- 不借用另一个纸面账户的现金或持仓；
- 不把纸面成交、状态正常或网页显示解释为真实订单证据；
- 不接入实盘，后续若讨论实盘必须作为新的独立设计重新审查。
